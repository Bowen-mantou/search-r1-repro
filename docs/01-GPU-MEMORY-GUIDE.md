# GPU 显存计算专题——从零学会算显存

> **配套项目**：Search-R1 复现（QLoRA 训练 Qwen3.5-4B、2×4090 训练 4B 全参数）。
> **读者画像**：跑过 GRPO 训练，但显存一直靠"抄别人的配置、报 OOM 就减 batch"的人；学过概率论但不知道四则运算还能这么用的人。
> **本文承诺**：只用到小学四则运算。每一个数字你都可以拿计算器复算。凡估算必标 ⚠️；凡"实际值"一定告诉你上哪查（config.json）。
> **对照物**：本文案例 A 的账目可读本项目 `agentic-rl-lab/03-search-r1/verl_search_r1/e6b_run.sh` 中部的"显存账"注释核对；案例 B 对应 `agentic-rl-lab/03-search-r1/train_grpo_local.py`。

在开始之前，先记住一句心法：

> **显存账 = 数清"有几个数组"，再算"每个数组多大"，最后加起来。**
> 数组多大 = 元素个数 × 每个元素几字节。就这么多。

## 第 1 章 字节与精度：一切的起点

**精度（dtype）**——一个数字在内存里用几个字节（byte）存储。字节数越多，表示越精确，但也越占地方。GPU 显存里存的每一个数字都有精度。

**参数量（P）**——模型里所有可学习的权重元素的总个数。比如"4B 模型"就是约 40 亿个参数。

### 1.1 精度字节表

| 精度 | 中文名 | 每个数占几字节 | 备注 |
|------|--------|--------------|------|
| fp32 | 32 位浮点 | 4 字节 | 最精确、最费钱，优化器状态默认用它 |
| fp16 | 16 位浮点 | 2 字节 | 省一半，但数值范围小，容易溢出 |
| bf16 | 16 位"脑浮点" | 2 字节 | 范围和 fp32 一样大、精度略低，训练首选 |
| fp8 | 8 位浮点 | 1 字节 | 更新的格式，推理加速用 |
| int8 | 8 位整数 | 1 字节 | 量化用，权重缩水 4 倍 |
| int4 | 4 位整数 | 0.5 字节 | 量化用，权重缩水 8 倍，QLoRA 的主力 |

这张表是全文的地基。**先把"4/2/2/1/0.5/1"这串数字背下来**，后面每一章都靠它。

### 1.2 两个换算口诀

```
口诀一（权重显存）：
    权重显存(字节) = 参数量 × 每参数字节数

口诀二（单位换算）：
    1 GB = 1024³ 字节 = 1,073,741,824 字节
    量级估算时：1 GB ≈ 10⁹ 字节（误差 7%，够用了）
```

为什么敢用 10⁹ 代替 1024³？因为我们做的是**量级估算**：判断"8GB 还是 80GB""爆不爆卡"。7% 的误差不影响任何结论。真要写论文再按 1024³ 精算。

### 1.3 三个例子（把口诀用一遍）

**例 1-1：4B 参数的模型，用 bf16 存权重，占多少显存？**

```
4×10⁹ 个参数 × 2 字节/参数 = 8×10⁹ 字节 ≈ 8 GB
```

**例 1-2：7B 模型 fp16：**

```
7×10⁹ × 2 = 14×10⁹ 字节 ≈ 14 GB
```

**例 1-3：70B 模型 bf16：**

```
70×10⁹ × 2 = 140×10⁹ 字节 ≈ 140 GB
```

看到规律了吗？**"B 数 × 2 = 显存 GB 数"**（fp16/bf16 时）。这就是为什么 70B 模型没法塞进 24GB 的 4090——光是权重就要 140GB，5 张卡都装不下。

> 补充一句严格口径：8×10⁹ 字节严格按二进制算是 7.45 GiB，不是 8 GiB。本文统一用"GB≈10⁹"的量级口径，误差已在上面声明过。

## 第 2 章 推理显存 = 权重 + KV cache

**推理（inference）**——只让模型生成答案、不更新参数的过程。推理时的显存只有两笔大账：

```
推理显存 ≈ 权重 W + KV cache
```

第一笔账（权重 W）上一章已经会算了：4B bf16 = 8GB。第二笔 KV cache 是本章的重头戏，我们从机制一步步推。

### 2.1 为什么会有 KV cache：自回归生成

**自回归生成（autoregressive）**——模型一个字一个字地吐：生成第 t 个字时，必须"看"前面全部 t−1 个字。每吐一个字，就多看一个字，再吐下一个。

问题来了：生成第 2 个字时算过一遍第 1 个字的注意力中间结果，生成第 3 个字时又要重新算一遍第 1、2 个字的——**如果不存结果，每吐一个字都要把全部历史重新算一遍，慢到没法用。**

**KV cache**——把每一层注意力算出来的两个中间矩阵 K（Key，钥匙）和 V（Value，值）存进显存，下次生成直接取用，不重算。本质是"**用显存换时间**"。

于是显存里多了一笔随生成长度增长的账：序列越长，缓存的历史 K、V 越多。

### 2.2 KV cache 公式，逐项拆解

```
KV 字节数 = 2 × n_layers × n_kv_heads × head_dim × seq_len × dtype_bytes × batch
```

七个因子，逐个解释（每个都问"为什么有它"）：

| 因子 | 含义 | 为什么有它 |
|------|------|-----------|
| 2 | K 和 V 两个矩阵 | 每层要存两份：钥匙一份、值一份 |
| n_layers | 层数 | **每一层**都有自己的 K/V，层数越多存得越多 |
| n_kv_heads | KV 头数 | 每层有多个注意力头，每个头各存各的（注意：用 **KV 头数**，不是查询头数——GQA 架构里多个查询头共用一组 KV 头，所以 KV 头更少） |
| head_dim | 每个头的维度 | 每个头里每个 token 有 head_dim 个数 |
| seq_len | 序列长度 | **每个 token 都占一份**——这就是"随生成长度线性增长"的来源 |
| dtype_bytes | 每数几字节 | 通常与权重同精度（bf16/fp16 = 2） |
| batch | 批大小 | 同时服务几条序列，就存几份 |

两个最容易懵的点单独说：

- **为什么乘 2**：注意力机制里 K（钥匙）和 V（值）是**两个不同的矩阵**，都要存。Q（查询）不存——因为生成第 t 个字时只用到"当前这个字"的 Q，用完就扔。
- **为什么乘 seq_len**：KV cache 存的是**每个历史 token** 各自的 K 和 V。序列有 2048 个 token，每层的 KV 就存 2048 份。所以 KV 显存和序列长度成正比——序列翻倍，KV 翻倍。

### 2.3 例 2-1：一条 2048 token 的序列，KV 占多少？

用 Qwen3.5-4B 举例。为教学方便，先用一组**示例配置**：36 层、8 个 KV 头、head_dim 128，bf16（2 字节），单条序列（batch=1）。

> ⚠️ **这组数是教学示例值，不是 Qwen3.5-4B 的真实配置**。真实配置在本章 2.5 节对照（32 层、4 个 KV 头、head_dim 256）。真实模型的每一项都要以它的 config.json 为准。

**第 1 步：一个 token、一层、一个头的 K 有多大**

```
1 个 token × 1 层 × 1 个头：
    head_dim = 128 个数
    × 2 字节   = 256 字节        （一个头的 K 是 256 字节）
```

**第 2 步：一个 token、一层（8 个头、K+V 两份）**

```
2 (K和V) × 8 个头 × 128 维 × 2 字节
= 2 × 8 × 128 × 2
= 4,096 字节 = 4 KiB          （一层里，一个 token 的 KV）
```

**第 3 步：一个 token、36 层**

```
4,096 字节/层 × 36 层
= 147,456 字节 = 144 KiB     （一个 token 的完整 KV）
```

**第 4 步：2048 个 token（竖式）**

```
  147,456 B/token     ← 每个 token 的 KV
×     2,048 token     ← 序列长度
───────────────
  301,989,888 B       ← 一条序列的全部 KV
  = 288 MiB ≈ 0.29 GB
```

**结论：一条 2048 token 的序列，KV cache 约 288 MiB ≈ 0.29GB。** 对照 8.4GB 的权重，单条序列的 KV 是小头；但注意它是**按序列长度线性涨**的——4096 token 就是约 0.58GB，8192 就是约 1.15GB，而且服务时要乘上**同时处理的序列条数**。

### 2.4 对照：Qwen3.5-4B 的真实 config.json

真实配置（`agentic-rl-lab/03-search-r1/sft_result/config.json`，即本项目的模型配置）：

| 项目 | 教学示例值 | 真实值（config.json） |
|------|-----------|---------------------|
| 层数 | 36 | **32** |
| KV 头数 | 8 | **4** |
| head_dim | 128 | **256** |

代入同样的四步：

```
2 × 4 头 × 256 维 × 2 字节 = 4,096 字节/层/token    ← 每层每 token 恰好也是 4 KiB
4,096 × 32 层 = 131,072 字节 = 128 KiB/token        ← 每 token 128 KiB
131,072 × 2,048 = 268,435,456 字节 = 256 MiB        ← 一条 2048 序列
```

有趣的是：教学示例值（36×8×128）和真实值（32×4×256）算出来居然接近（288 vs 256 MiB）——因为 8×128 和 4×256 恰好相等。**但这是巧合，不是理由**。真正要记住的是：**KV 头数、层数、维度，全部以 config.json 为准，抄别人的配置值必翻车。**

> ⚠️ 进阶提示：Qwen3.5-4B 是混合架构（32 层里只有 8 层是全注意力，24 层是线性注意力）。线性注意力层维护的是**固定大小**的循环状态、不随序列增长，真正"随 seq_len 线性增长"的 KV 只有那 8 层全注意力。所以严格算：128 KiB/token × (8/32) × 2048 = 64 MiB。**混合架构模型要分层算账**——这正是"以 config.json 为准"的深层含义。

### 2.5 例 2-2：vLLM 的 gpu_memory_utilization=0.75，24GB 卡上 KV 池多大？

**gpu_memory_utilization**——vLLM 的参数，表示"允许 vLLM 最多使用整卡显存的百分之几"。设 0.75 就是允许用 75%。

```
0.75 × 24 GB = 18 GB        ← vLLM 的总预算（不是全给 KV！）
```

这 18GB 要先扣掉两笔：

```
18 GB - 8.4 GB（模型权重） = 9.6 GB
9.6 GB - ~1.5 GB（激活峰值缓冲、CUDA graph 等 ⚠️ 估算） ≈ 8 GB
```

所以 KV 池大约 **8GB 左右**（⚠️ 激活缓冲是估算值，vLLM 启动日志里会打印实测的 KV cache 可用量，以日志为准）。

8GB 的 KV 池能装多少 token？用真实配置的 128 KiB/token：

```
8 GiB = 8 × 1024³ = 8,589,934,592 字节
8,589,934,592 ÷ 131,072 B/token = 65,536 token
```

**约 6.5 万 token 的池子**。如果平均每条请求 2048 token，就能同时服务约 30 条；如果平均 4096 token，就只能约 16 条。这就是为什么"限制 max_num_batched_tokens / 最大并发"能防 KV 撑爆——池子大小是固定的。

**为什么要预留（PagedAttention 一句话）**：vLLM 把 KV 按固定大小的"页"切块分配（像操作系统的内存分页），启动时**一次性预留整块池子**并做好分页管理，避免服务中途碎片化或 OOM。gpu_memory_utilization 就是控制这个池子多大——留太大挤爆训练侧，留太小并发上不去。

## 第 3 章 训练显存五件套（核心章）

**训练（training）**——不只前向算答案，还要反向传播、更新参数。显存账单立刻变厚。先把五个名词一次性摆出来：

1. **权重 W**——模型参数本身。
2. **梯度 G（gradient）**——反向传播算出的"每个参数该改多少"，和 W 一样大。
3. **优化器状态 O（optimizer state）**——Adam 记的"账本"（一阶矩 m、二阶矩 v）。
4. **激活 A（activation）**——前向传播时每层的中间结果，反向传播要翻出来用。
5. **主权重副本（master weight，fp32 主副本）**——混合精度训练时另存的一份高精度权重。

一件件算。

### 3.1 权重 W

第 1 章算过：4B bf16 = 8GB。训练时权重常驻显存，因为每步都要用它算输出。

### 3.2 梯度 G

反向传播给**每个参数**算一个梯度值，所以梯度的形状和权重一模一样：

```
G = W = 4×10⁹ × 2 字节 = 8 GB
```

梯度通常在训练时保持和权重相同的 dtype（bf16/fp16），所以 G = W。

### 3.3 优化器状态 O：Adam 为什么是 8 字节/参数

**Adam（Adaptive Moment Estimation）**——最常用的优化器：给每个参数维护两个"账本"：

- **一阶矩 m**：梯度的"滑动平均"（大致理解成"最近一直在往哪个方向推"）；
- **二阶矩 v**：梯度平方的滑动平均（大致理解成"这个参数的梯度波动有多大"）。

关键：**m 和 v 的形状都和参数一模一样**（每个参数各记一笔），而且为了数值稳定都存 fp32（4 字节）。于是：

```
m： 4 字节/参数   ← fp32
v： 4 字节/参数   ← fp32
─────────────────
O = 8 字节/参数   ← Adam 的代价

4B 模型：4×10⁹ × 8 = 32 GB
    其中 m = 16 GB，v = 16 GB
```

竖式验证：

```
  4×10⁹ 参数
×     8 字节/参数
─────────────
 32×10⁹ 字节 = 32 GB     ✓ 是权重(8GB)的 4 倍
```

两个常见问题：

- **AdamW 呢？** AdamW 只是 Adam 改了权重衰减的做法，**不多存任何东西**，一样是 8 字节/参数。
- **SGD 呢？** 纯 SGD 没有 m、v，0 字节/参数；带 momentum（动量）的 SGD 只存一份动量 = 4 字节/参数。所以 SGD 训练显存远小于 Adam——代价是收敛通常更慢、要调更多超参。

看到这里你应该明白了训练显存的大头在哪：**权重只占 1 份，Adam 状态占 4 份（8 字节 vs 2 字节）。**

### 3.4 激活 A：最捉摸不定的一笔

**激活（activation）**——前向传播时每层算出来的中间结果（比如注意力层的 Q、K、V，MLP 的输出）。反向传播要用它们算梯度，所以**前向时先存起来**。

激活的量级取决于"**一次前向要同时算多少 token**"：batch × seq_len 越大，中间结果的张量越大。

粗估一下量级（Qwen3.5-4B，hidden=2560，bf16）：

```
每层中间结果 ≈ 约 20 个 [batch, seq_len, 2560] 形状的张量 × 2 字节
             ≈ 20 × 2560 × 2 ≈ 100 KB / token / 层     ⚠️ 粗估
× 32 层       ≈ 3.2 MB / token
× 2048 token  ≈ 6.6 GB   ← 不开梯度检查点，一条 2048 序列的前向激活
```

⚠️ 以上是粗估（"约 20 个张量"取决于模型结构），但量级结论可靠：**长序列 + 大 batch 时，激活可以比权重还大**。GRPO 训练 prompt+response 动辄 4096-8192 token，激活最容易爆。

**梯度检查点（gradient checkpointing）**——前向时不存全部中间结果，只存每层**输入**的"检查点"；反向传播需要哪层的中间结果，就用检查点**现场重算一遍**。口诀：**"用重算的时间，换激活的显存"**。

```
开检查点后：
  每层只存 1 个输入张量 ≈ 5 KB / token / 层
  × 32 层 × 2048 token ≈ 0.3 GB   + 当前微批的反向中间量
  实测量级：1-3 GB  ⚠️ 经验法则（本项目 e6b 账目按 ~1.5GB 记）
```

**经验法则：小 batch（每卡 1 条 2048-4096 token）开梯度检查点，激活 1-3GB；序列长度翻倍，激活跟着翻倍；不开检查点，乘 20 倍。** 本项目脚本里 `enable_gradient_checkpointing=true` 就是干这个的。

### 3.5 混合精度与 master weight

**混合精度训练**——权重和计算用 bf16（快、省显存），但 bf16 精度低，**直接用它累加更新会丢精度**。于是维护一份 **fp32 的主权重副本（master weight）**：每步在 fp32 里做真正的参数更新，再拷回 bf16 做前向。

代价：**每个参数多 4 字节**。

```
master weight = 4 字节/参数 × 4×10⁹ = 16 GB
```

### 3.6 总账：训练显存公式

```
训练显存 ≈ W + G + O + A          ← 基准账（全参数、单卡、无量化）
混合精度（bf16 训练）再加：
          + master（4 字节/参数）
```

换算成"每参数几字节"的口诀（bf16 + Adam）：

| 件 | 每参数字节 | 4B 模型 | 来源 |
|----|-----------|---------|------|
| W | 2 | 8 GB | bf16 |
| G | 2 | 8 GB | 同 W |
| O（Adam m+v） | 8 | 32 GB | fp32 × 2 份 |
| master | 4 | 16 GB | fp32 × 1 份 |
| **合计** | **16** | **64 GB** | **16 字节/参数口诀** |
| A | 视 batch×seq | 1-3 GB ⚠️ | 开检查点 |

**"16 字节/参数"是全文最重要的口诀**：bf16 混合精度 + Adam 的全参数训练，每 1B 参数约 16GB 显存（不含激活）。

马上就能用它推三个数：

```
4B 模型  → 16×4  = 64 GB   → 单卡 24GB 必爆（要 3 张以上 24GB 卡）
7B 模型  → 16×7  = 112 GB  → 4×24GB 也不够
70B 模型 → 16×70 = 1,120 GB ≈ 1.1 TB  → 必须多机
```

反过来说：**24GB 的卡，无 offload 全参训练的上限约 1.5B 参数**（24 ÷ 16 = 1.5）。记住这两个数，别人忽悠不了你。

## 第 4 章 省显存的四板斧

64GB 的需求怎么塞进 12GB、24GB 的卡？四板斧：**量化、LoRA、分片、offload**。

### 4.1 第一板斧：量化（权重瘦身）

**量化（quantization）**——把权重从高精度存成低精度。int8 = 1 字节/参数（4 倍压缩），int4 = 0.5 字节/参数（8 倍压缩）。只量化**权重**，计算时再临时解回高精度（所以激活和梯度照旧占地方）。

4B 模型的权重在各种精度下的体积：

| 精度 | 每参数 | 4B 权重 |
|------|--------|---------|
| bf16/fp16 | 2 | 8 GB |
| fp8 / int8 | 1 | 4 GB |
| int4 | 0.5 | 2 GB |

int4 之后 4B 权重只剩 **2GB**——一张 3060 都能装下。这就是 QLoRA 的"Q"。

**NF4（4-bit NormalFloat）**——int4 的一种具体格式，专为神经网络权重分布设计，量化损失更小；**双重量化（double quant）**——连"量化用的缩放系数"也量化一遍，再省一点点。本项目 `train_grpo_local.py` 里 `load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_use_double_quant=True` 就是这三样。

### 4.2 第二板斧：LoRA（只训练旁路）

**LoRA（Low-Rank Adaptation）**——冻结原模型的全部权重，只在每个目标层旁边**并联两个小矩阵** A 和 B（A：d×r 降维，B：r×d 升维），只训练这两个小矩阵。原层照常算，旁路输出加上去。

- **r（秩）**：旁路的"窄腰"，典型值 8-64。r 越大旁路越宽、可训参数越多。
- **d（hidden_size）**：模型隐藏维度，Qwen3.5-4B 是 2560。
- 好处：**梯度、Adam 状态、master 都只给旁路那一点点参数**，原模型的权重一个字节都不用动。

旁路参数量公式：

```
一个模块的旁路参数 = A 的参数 + B 的参数
                 = r × d    +  d × r
                 = 2 × r × d
总旁路参数 = 2 × r × d × 每层模块数 × 层数
```

代入本项目真实配置（`train_grpo_local.py`：r=16，目标模块 q/k/v/o/gate/up/down 共 7 个，32 层，d=2560）：

```
每模块：2 × 16 × 2560 = 81,920 参数
每层  ：81,920 × 7 = 573,440 参数
全模型：573,440 × 32 = 18,350,080 ≈ 18.35M 参数
占比  ：18.35M ÷ 42 亿 ≈ 0.44%    ← 可训参数不到千分之五
```

> ⚠️ 注：如果 r=32（部分配方会用），旁路翻倍到约 36.7M，"几十 M 量级"的说法由此而来；r、目标模块数、层数都会改变结果，**以你的 LoRA 配置代入为准**。

然后给这 18.35M 参数算"五件套"：

```
LoRA 权重    ：18.35M × 2 字节 = 36.7 MB
LoRA 梯度    ：36.7 MB
LoRA 的 Adam ：18.35M × 8 字节 = 146.8 MB
LoRA 的 master：18.35M × 4 字节 = 73.4 MB
──────────────────────────────
合计 ≈ 294 MB ≈ 0.3 GB          ← 原模型 8GB 全参训练要 64GB，旁路只要 0.3GB
```

**这就是 LoRA 的魔法：训练侧的 W/G/O/master 从 64GB 级别缩到 0.3GB 级别。**

### 4.3 第三板斧：FSDP 分片（人多力量大）

**DDP（分布式数据并行）**——每张卡放**一整套**模型副本，各算各的数据、再对梯度求平均。显存：**每卡一份全量** W+G+O——卡多了显存不降，纯加速。

**FSDP（Fully Sharded Data Parallel，全分片数据并行）**——把 W、G、O **切碎**分到 N 张卡上，每张卡只持有 1/N。计算某层时临时把该层的完整参数"聚"过来，算完立刻"散"回去：

- **unshard（聚合）**：把切碎的权重 all-gather 成完整一份；
- **compute（计算）**：正常前向/反向；
- **reshard（释放）**：用完立刻扔掉全量副本，只留自己的 1/N。

于是：

```
DDP  ：每卡显存 = 全量(W+G+O) + A        ← 卡越多越没用
FSDP ：每卡显存 = (W+G+O)/N + A          ← 显存随卡数线性下降
```

4B 全参（64GB）对比：

| 方案 | 每卡账目 | 24GB 卡 |
|------|---------|---------|
| DDP（任意卡数） | 64 GB + 激活 | 必爆 |
| FSDP 2 卡 | 64/2 = 32 + 激活 | 爆 |
| FSDP 4 卡 | 64/4 = 16 + 激活 ~2 ⚠️ | ≈18GB ✓ |

注意 7B 用 FSDP 4×24GB：112/4 = 28GB/卡，**仍然爆**——所以 7B 全参要么更多卡，要么搭配下一板斧。

> 一句话细节：unshard 的瞬间，本卡同时持有"自己的 1/N 分片"和"聚合出的全量参数"，峰值是 W + W/N 而不是 W——这正对应本项目 e6b_run.sh 里 `layered_summon=true`（分层聚合，避免全量 8.4GB 与分片同时驻留把峰值顶爆）的原因。

### 4.4 第四板斧：CPU offload（把账本搬回家）

**Offload**——把 GPU 显存放不下的东西搬到 **CPU 内存**（RAM）里，用到时再搬回来。最常用的是 **optimizer offload**：把 Adam 的 m、v（fp32，最大的一笔）放内存；进阶的 **param offload** 把权重也放内存，GPU 只留"正在用的那部分"。

代价是什么？**搬家的速度差两个数量级**：

```
GPU 显存带宽：约 1-3 TB/s
PCIe 总线带宽：约 16-32 GB/s     ← CPU 和 GPU 之间只有这条小路
```

每步训练要把 m、v、master 从内存搬进 GPU、更新完再搬回去——来回搬运的时间全加在步时上。本项目 e6b_run.sh 注释实测口径：**开 optimizer+param offload 后，每步 +30-60 秒**。显存和速度永远在做交换：**省了显存，就付时间。**

## 第 5 章 三个实战案例（从头算到尾）

### 案例 A：2×4090（24GB×2）训 Qwen3.5-4B 全参数（本项目真实账）

**场景**：veRL 全参数 GRPO，模型 wang072266/qwen3.5-4b-search-r1-sft，FSDP 双卡。账目可读 `agentic-rl-lab/03-search-r1/verl_search_r1/e6b_run.sh` 中部的"显存账"注释核对。

**先定基数**：本项目按权重 8.4GB 记账（bf16，即参数约 42 亿 ⚠️ 以模型实际为准）。逐件写账：

```
W   = 8.4 GB                     ← 权重（bf16）
G   = 8.4 GB                     ← 梯度（同 W）
O   = 25.2 GB = 8.4 × 3          ← Adam 侧：m、v、master 各一份 8.4（见下方 ⚠️ 口径说明）
vLLM 权重 = 8.4 GB               ← 推理引擎自己再持有一份完整权重（rollout 用）
A   ≈ 1.5 GB                     ← 激活（开了梯度检查点 ⚠️ 脚本口径）
```

**第一步：不开 offload 会怎样？**

```
每卡 = (W + G + O + vLLM 权重) / N + A
     = (8.4 + 8.4 + 25.2 + 8.4) / N + 1.5
     = 50.4 / N + 1.5

N=1：50.4 + 1.5 = 51.9 GB  > 24 GB  ❌ 爆
N=2：25.2 + 1.5 = 26.7 GB  > 24 GB  ❌ 还是爆
```

两张 4090 都不够——**Adam 那一笔 25.2GB 是最大头**（比权重、梯度加起来还多）。

> ⚠️ **"25.2 = 8.4×3"的口径说明**：e6b_run.sh 注释把 Adam 侧按三份 8.4GB 记：m 一份、v 一份、fp32 主副本一份，每份约等于 bf16 权重的大小——这是**快速推算口径**。严格按第 3 章公式，fp32 一份是 4 字节/参数 = bf16 的 2 倍，即 m、v、master 各 16.8GB、合计 50.4GB；严格口径下无 offload 每卡 = (8.4+8.4+50.4+8.4)/2 + 1.5 = 39.3GB。**两种口径结论完全一致：必爆。**脚本注释是"推算"不是"实测"，教学时认结构、不背数字。

**第二步：开 optimizer + param offload（脚本实际做法）**

把 Adam 状态（m+v+master）和参数都搬到 CPU 内存，GPU 上训练侧只剩：

```
训练侧 = G/N + A = 8.4/2 + 1.5 = 4.2 + 1.5 = 5.7 GB

推理侧（vLLM 池）≈ 13.2 GB     ⚠️ 注释口径
总占用 ≈ 5.7 + 13.2 = 18.9 GB  < 24 GB  ✓
余量 ≈ 24 - 18.9 = 5.1 GB ≈ 余 4-5 GB（再扣 CUDA 上下文、碎片 ~1GB）
```

> ⚠️ "13.2GB"的说明：这是 e6b_run.sh 注释给 vLLM 预留的池子上限（注释原话"vLLM(0.45/0.55 池)"，N=2 对应 13.2）。注意它和 `gpu_memory_utilization=0.75` 不是同一个数：0.75×24 = 18GB 是 vLLM 的总预算口径，扣掉 vLLM 自身权重 8.4GB 后纯 KV 池约 5-10GB 量级；不同 vLLM/veRL 版本对"utilization 按整卡还是按剩余显存计算"口径不同。**训练启动后以 vLLM 日志打印的 KV cache 容量为准。**

**结论**：2×4090 训 4B 全参数，无 offload 必爆；开 optimizer+param offload 后每卡约 18.9GB，余 4-5GB，能跑。**代价**：参数和优化器状态每步经 PCIe 流式进出，步耗时 +30-60 秒。顺带一提：降级到单卡（N=1）时训练侧 8.4+1.5 = 9.9GB + vLLM 池 10.8GB ≈ 20.7GB，也装得下（⚠️ 注释口径）。

### 案例 B：单卡 RTX 3060 12GB 训 4B 的 QLoRA（本项目本地管线）

**场景**：`agentic-rl-lab/03-search-r1/train_grpo_local.py`——4-bit QLoRA，AutoDL 3060 12GB。

**第一步：先算全参数会怎样**

```
4B 全参 = 16 字节/参数 × 4×10⁹ = 64 GB  ≫ 12 GB   ❌ 5 倍爆卡，想都别想
```

**第二步：QLoRA 逐项账**

| 项 | 算式 | 结果 |
|----|------|------|
| 4bit 基座权重 | 4×10⁹ × 0.5 字节 | 2.0 GB（实际参数 42 亿 → 2.1GB ⚠️） |
| LoRA 旁路权重 | 18.35M × 2 字节（r=16，见 4.2 节演算） | 0.037 GB |
| LoRA 梯度 | 同旁路权重 | 0.037 GB |
| LoRA 的 Adam | 18.35M × 8 字节 | 0.147 GB |
| LoRA 的 master | 18.35M × 4 字节 | 0.073 GB |
| 激活（开梯度检查点） | 经验法则 ⚠️ | 1-3 GB |
| **合计** | | **≈ 3.3-5.3 GB < 12 GB ✓** |

**结论**：基座 2GB + 旁路全家桶 0.3GB + 激活 1-3GB ≈ 3-5GB，12GB 卡余一半。**为什么能跑**：量化把权重砍到 2GB；LoRA 把"梯度+Adam+master"从 64GB 量级砍到 0.3GB；梯度检查点再按住激活。三斧齐下，64GB → 5GB。

### 案例 C：想训 7B / 70B 怎么办（查表式回答）

**7B（bf16 全参 + Adam + master）：**

```
W 14 + G 14 + m 28 + v 28 + master 28 = 112 GB   （16 字节/参数 × 7B）
```

| 方案 | 账目 | 结论 |
|------|------|------|
| 单卡 24GB | 112 ≫ 24 | ❌ 必爆 |
| 4×24GB FSDP 无 offload | 112/4 = 28GB/卡 | ❌ 仍超 |
| 6×24GB FSDP | 112/6 ≈ 18.7 + 激活 ~2 ⚠️ ≈ 21GB/卡 | ✓ 可行 |
| 4×24GB + optimizer offload 或 8-bit Adam | 显存大头搬走/减半 ⚠️ | ✓ 常用 |
| 2×80GB FSDP | 56 + 激活 | ✓ 轻松 |
| QLoRA（4bit + LoRA） | 基座 3.5GB + 旁路 ~0.3 + 激活 | ✓ 单卡 24GB，甚至 16GB ⚠️ |

**70B（bf16 全参）：**

```
W = 140 GB
Adam m+v = 8 字节/参数 × 70×10⁹ = 560 GB
master = 280 GB，G = 140 GB
合计 = 140 + 560 + 280 + 140 = 1,120 GB ≈ 1.1 TB
```

| 方案 | 账目 | 结论 |
|------|------|------|
| 全参 ZeRO-3 多机 | 1,120/80 = 14 → 16×80GB（留激活余量） | ✓ 标准做法 |
| 8×80GB + ZeRO-3 CPU offload | 优化器状态下放内存 ⚠️ | ✓ 省一半卡 |
| QLoRA | 4bit 基座 35GB + 旁路小头 | ✓ 1×80GB 可训 LoRA |

> ⚠️ 本章卡数全是"无激活/少量激活"口径的经验估算，长序列大 batch 时要另加激活、KV、余量，实际以训练日志的峰值显存为准。但**量级结论**是可靠的：先按 16 字节/参数估全参总账，再看卡数够不够分。

### 题 1：7B 模型 bf16 的权重显存

<summary>答案</summary>

```

### 题 2：Adam 训练 1B 模型的优化器状态显存

<details>
<summary>答案</summary>

```
m：1×10⁹ × 4 = 4 GB
v：1×10⁹ × 4 = 4 GB
O = m + v = 8 GB     （AdamW 相同；SGD+momentum 只有 4 GB）
```

### 题 3：一条 4096 token 序列的 KV cache

模型：32 层、8 个 KV 头、head_dim 128、bf16、batch=1。

<details>
<summary>答案</summary>

```
每 token：2 × 32 × 8 × 128 × 2 字节 = 131,072 字节 = 128 KiB
整条序列：131,072 × 4,096 = 536,870,912 字节 = 512 MiB

  131,072 B/token
×     4,096 token
───────────────
  536,870,912 B = 512 MiB
```
对比题 1：权重 14GB，一条 4096 序列的 KV 是它的 1/28；但 batch=32 的 4096 序列就是 16GB，超过权重。
</details>

### 题 4：3×A100（80GB）能否全参训 13B？

条件：bf16 + Adam + master，FSDP，无 offload。列出算式。

<details>
<summary>答案</summary>

```
总账 = 16 字节/参数 × 13×10⁹ = 208 GB
每卡 = 208/3 ≈ 69.3 GB + 激活 ~2 GB（⚠️ 经验值）≈ 71.3 GB < 80 GB ✓

逐件验证：W 26 + G 26 + m 52 + v 52 + master 52 = 208 GB ✓
```
**能训**，余约 8.7GB。顺带记住：13B 是"80GB 卡 3 张能带动的上限量级"。
</details>

### 题 5：2×4090 训 4B 全参，为什么必须开 offload

把案例 A 独立重算一遍。

<details>
<summary>答案</summary>

```
基数：W 8.4，G 8.4，Adam 侧 25.2（= 8.4×3：m、v、master），vLLM 权重 8.4，激活 1.5

无 offload：每卡 = (8.4+8.4+25.2+8.4)/2 + 1.5
                    = 50.4/2 + 1.5 = 25.2 + 1.5 = 26.7 GB > 24 GB ❌ 爆

开 optimizer+param offload：
    训练侧 = G/N + A = 4.2 + 1.5 = 5.7 GB
    + vLLM 池 ≈ 13.2 GB（⚠️ 注释口径）
    = 18.9 GB < 24 GB ✓ 余 ~4-5 GB

大头是 Adam 侧 25.2GB：两张卡分下来 12.6GB，加上权重、梯度、vLLM 权重就顶穿 24GB。offload 把 Adam 侧和参数搬去内存，GPU 只留梯度和激活，问题解决——代价是每步 +30-60 秒。
</details>
