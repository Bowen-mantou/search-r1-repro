# Search-R1 面试问答手册（28 题全解）

>
> 1. **每个数字都能说出测量方法**。面试官追问"这个 81.2% 怎么来的"时，
>    你要能答出"训练 step 3 的批次内 64 条轨迹 EM 比例，由训练脚本每步
>    打印，PyTRIO 平台记录"。本文每个数字后面都附了测量方法。

## 项目动机类

### Q1. 为什么选 Search-R1 这个项目？

**背景**：我在做 agentic RL 方向的实践，需要一个「RL × 检索 × 多轮交互」
三者交叉的项目。Search-R1 是 2025 年这个方向的代表性工作（检索在环 RL），
而且开源生态完整（论文 + 官方实现 + 教程仓库），适合独立复现和改造。

**原理**：Search-R1 把搜索引擎变成 RL 环境里的工具：模型输出 `<search>` 标签
触发真实检索，检索结果注入上下文，最终答案决定奖励。训练目标只有一个
outcome reward（答案对错），却能涌现出"判断、检索、整合"三类能力——
这是它有意思的地方：稀疏奖励下的行为涌现。

**我的做法**：没有停在复现，而是搭了完整流水线并做了 6 项改进：教师蒸馏
（397 条轨迹）→ SFT 冷启动 → GRPO，加异常轨迹过滤、LLDS 正则化
（解决训练崩溃）、PRM-Lite 过程奖励、LATA 长度归一、5 种可插拔搜索后端；
最后把训练从本地 QLoRA 脚本迁移到 veRL 全参数多卡框架，做了一次完整的
分布式训练工程化（OOM 修复、API 对齐、性能瓶颈分析）。

**数据**：本地管线 correct_rate 峰值 81.2%；SFT loss 1.65→0.11；veRL 侧
2×4090 显存 18.9GB/卡（余 4GB）。

**反思**：这个项目最大的价值不是某个指标，而是把"算法想法 → 训练崩溃 →
稳定性修复 → 生产框架迁移"整条链路走了一遍。选项目我建议选"能自己
改进出差异"的，而不是只能复现的。

### Q2. 为什么选 GRPO 而不是 PPO/DPO？GRPO 相对 PPO 省了什么？

**背景**：Search-R1 官方配方就是 GRPO，但我是先想清楚"为什么"才跟的。

**原理**：PPO 需要 4 个模型：Actor（生成）、Critic（价值估计）、Reference
（KL 锚点）、Reward。Critic 的价值函数训练是整个 RLHF 里最不稳定、最贵
的部分。GRPO 的核心洞察：**同一道题的 N 条采样轨迹互相比较，就能得到
相对优势，不需要绝对价值估计**——`A_i = (r_i − mean) / std`（组内归一）。
DPO 是离线偏好对齐：不需要采样和在线交互，但它的数据分布（偏好对）和
推理分布不一致，且天然不适合"工具调用"这种多轮交互任务（偏好对难以
标注"搜索轨迹 A 比 B 好在哪里"）。

**我的做法**：本地管线 group_size=8（每题 8 条轨迹算组内 advantage），
veRL 管线 n=4。显存账（4B 模型、bf16）：PPO 全参数约 92GB（含 critic
的权重+梯度+Adam），GRPO 约 50GB——省掉的是 Critic 的全部开销
（权重 8.4 + 梯度 8.4 + Adam 25.2 ≈ 42GB，接近一半）。

**数据**：GRPO 在 2×4090（48GB 显存总量）上靠 offload 就能训 4B 全参数，
PPO 同配置下没有可能。测量方法：显存分解公式（权重 8.4GB = 4B×2B，
Adam 状态 = 权重×3）加实测日志（训练侧 allocated 峰值 18.9GB/卡）。

**反思**：GRPO 适合"答案可自动判分"的任务（数学、检索问答），因为
组内比较需要一个可靠的标量 reward；开放式任务（写作）没有自动判分器，
组内优势的方差会爆炸，那是 Critic 或 judge model 的用武之地。

### Q3. RAG 和 Agentic Search 的区别？为什么训练模型「学会搜索」比写死检索流程好？

**背景**：面试里这个问题考的是你对"检索增强"光谱的理解。

**原理**：RAG = 检索与生成**解耦**（固定检索器召回 → 拼接 prompt →
LLM 回答），模型对检索零决策权。Agentic Search = 检索是模型的**工具**，
何时搜、搜什么、搜几轮、怎么用结果全是模型的行为。写死流程假设
"最优检索策略已知"，训练模型则让策略从奖励信号中涌现：多跳问题
先搜实体再搜属性、简单问题不搜、结果矛盾时换 query——这些规则
写死是组合爆炸，学出来是自然的。

**我的做法**：训练时把搜索做成工具调用协议（`<tool_call>` + 系统提示
定义 search 函数），GRPO 用 outcome reward 优化整个搜索-回答行为链。

**数据**：dev 集 70 题：SFT 冷启动模型（没经过 RL）EM 1.43%、平均搜索
0 次——它根本没学会调用工具；GRPO 训练后 correct_rate 81.2%、平均搜索
1-2.8 次。「搜索」行为本身是 RL 逼出来的，这是"训练 > 写死"最直接的
证据。测量方法：eval_local.py greedy 解码 + EM 精确匹配 + 轨迹里
search_calls 字段统计。

**反思**：诚实说，RAG 在生产上依然便宜可靠（延迟可控、可解释）；Agentic
Search 的优势在多跳推理和不可搜索问题的判断上。面试讲这个要平衡——
不要踩 RAG，要讲清两者适合的场景。

### Q4. 为什么基座选 4B？显存账怎么算的？

**背景**：预算约束下的选型问题，不是"越大越好"。

**原理**：训练显存 = 权重 + 梯度 + 优化器状态 + 激活 + 推理引擎的
KV cache。全参数 bf16 训练时：权重 2B/参数，Adam 状态（m+v 各一份
fp32）≈ 8B/参数，梯度 2B/参数。4B 模型 = 权重 8.4GB、Adam 25.2GB、
梯度 8.4GB。7B 全部 ×1.75，单卡装不下，必须多卡分片。

**我的做法**：预算红线（veRL 阶段 ¥43、总预算 ~¥164）下算了两笔账：
① 本地 QLoRA：4-bit 量化 + LoRA 只需 ~8GB 显存，3060（¥1/h）就能跑；
② veRL 全参数：2×4090（¥4.36/h）开 optimizer+param CPU offload 后
每卡 18.9GB（余 4GB），50 步预计 ¥22-28。Qwen3.5-4B 本身是
Transformer+Mamba 混合架构，还顺手踩了 Mamba cache block 的适配坑
（这是 7B 纯 Transformer 遇不到的）。

**数据**：显存公式：无 offload 每卡 = 50.4/N + 1.5GB（N=2 时 26.7GB
必爆，vLLM 权重还没算）；开 offload 后训练侧只剩梯度 4.2 + 激活 1.5
+ vLLM 池 13.2 ≈ 18.9GB。测量方法：公式推算 + nvidia-smi /
torch.cuda.memory_allocated 日志验证。

**反思**：选模型大小的正确顺序是"先算显存和预算，再定模型"。4B 不是
最优模型，是"预算内能跑全参数 + 足够学到搜索策略"的最小可行解。
如果预算翻倍我会直接上 7B 并做 4B/7B 的 scaling 对比。

## 算法细节类

### Q5. GRPO 的 advantage 怎么算？组内归一化的数学和直觉？

**背景**：GRPO 的核心公式，必考题。

**原理**：对同一问题 q 采样 N 条轨迹，奖励 r_1...r_N：
`mean = Σr_i/N`，`std = sqrt(Σ(r_i−mean)²/N)`，
`A_i = (r_i − mean)/(std + ε)`。直觉：同一道题内部比较——答对的轨迹
相对于"这道题的平均水平"是正优势，答错的是负优势。组内归一化让
advantage 尺度无关（reward 是 0~1 还是 0~100 都无所谓），也自动
处理了题目难度差异（难题组和简单题组各自归一）。

**我的做法**：`compute_group_advantages` 里两个工程细节：① 先排除
异常轨迹再算 mean/std——异常轨迹的 reward 极端（全 −0.1），会让
正常轨迹的 advantage 被虚高/虚低；② `std + 1e-8` 防除零（全组
reward 相同时 advantage 全 0，该组无信号，正确跳过）。

**数据**：8 条轨迹、4 对 4 错时：mean=0.5、std≈0.535、advantage≈±0.93。
测量方法：构造样例手算 + test 用例验证。

**反思**：组内归一化的隐含假设是"同题轨迹可比"——如果同一题的不同
轨迹搜索环境差异巨大（比如一半搜索失败），advantage 会被环境噪声
污染，这是异常过滤存在的理由。

### Q6. KL 约束在 GRPO 里怎么做的？为什么需要 KL？

**背景**：RL 的经典问题：策略优化只朝高奖励方向走，会把模型"改坏"。

**原理**：RL 目标 max E[r]，纯策略梯度会无约束地改变输出分布——
奖励有漏洞就钻（reward hacking），分布漂移后生成质量崩坏。KL 惩罚
`−β·KL(π_θ || π_ref)` 把策略锚在参考模型附近，是"安全带"。
GRPO 论文在 reward 里减 KL；veRL 里通常用 `use_kl_loss` 开 ref 模型
在 loss 里加 KL 项。

**我的做法**：本地管线用 **LLDS 替代 KL 的防崩职责**（见 Q7）——它是
单向的（只罚似然下降，不拖慢正常学习）。veRL 管线**主动关掉 KL**
（`use_kl_loss=false`）：一是 Search-R1 官方 GRPO 配方本来无 KL 项；
二是实测 veRL 0.10 的 ref CPUOffload 在 torch 2.13 下不生效（ref
常驻 GPU 8.46GB），关 KL 省下这 8.46GB 让 2×4090 能跑起来。

**数据**：ref 常驻 8.46GB 的测量方法：日志里 ref FSDP 初始化后
`allocated 8.46GB` 不再下降（offload 应降到 ~0）。

**反思**：KL 和 LLDS 是同一个问题的两个答案——KL 是"对称的橡皮筋"
（拉回参考分布），LLDS 是"单向的地板"（只防变坏）。哪个更好取决于
你怕的是"漂移"还是"崩坏"；Search-R1 这类格式敏感任务，崩坏是
主要矛盾，单向约束更合适。

### Q7. LLD 死亡螺旋是什么？你的 LLDS 怎么修？v1 为什么失败、v2 为什么成功？

**背景**：我项目里最硬核的实战问题，值得展开讲。

**原理**：LLD（Lazy Likelihood Displacement，ICML 2026 有同主题论文，
我撞上时独立发现了现象）：GRPO loss = −A·log π。当组内方差大时
advantage 幅度大，负优势 token 的似然被狠狠压低；被压低的 token
导致 rollout 质量变差 → reward 方差更大 → advantage 更大 → 压低更狠
——正反馈。**特征：reward 指标还在高位，log-likelihood 持续下降**，
直到输出熵崩、格式全乱。

**我的做法**：LLDS 惩罚 `λ·Σ max(0, log π_ref − log π_θ)`：
- π_ref 是 rollout 时旧策略的 token logprob（采样时顺手存下来）；
- 当前似然高于参考 → max(0,负数)=0 不惩罚；低于参考 → 按差距惩罚；
- 单向性是灵魂：只挡"变坏"，不拖"变好"。
- 三变体：R（轨迹总似然门控）、A（逐 token，仅 advantage≠0）、
  MA（只罚工具 token，保护答案 token）。

**数据**：
- E1-A 无 LLDS：56 步 correct 3.1%（从峰值 81.2% 崩掉）。
- v1（固定偏移 λ=0.05）：最高 71.9%，step 63 崩到 1.6%。
  **失败原因**：固定惩罚相对 GRPO 优势梯度太弱，优势项一放大就淹没它。
- v2（比例缩放，惩罚 ∝ 似然下降量，早期带 min(delta,10) 上限）：最高
  81.2%（step 3），**低点能恢复**（3.1%→54.7%），不再永久崩溃。
- 测量方法：PyTRIO 训练日志每步打印 correct_rate（批次内 EM 比例）。

**反思**：两个通用教训：① 正则化强度必须与被防护量**同阶**——固定
惩罚挡不住幅度变化，比例惩罚自动匹配梯度大小；② "reward 上升"≠
"训练健康"，监控 log-likelihood 才能提前看到死亡螺旋。

### Q8. PRM-Lite 的 22 条规则设计思路？为什么 cap 在 [-0.2, +0.2]？

**背景**：过程奖励能解决 outcome reward 稀疏的问题，但真 PRM 太贵。

**原理**：真 PRM 要训练模型给每个中间步骤打分，成本高且有
"过程分涨了最终答案没涨"的 reward hacking 风险。PRM-Lite 用
**规则**给搜索行为打分：12 条惩罚（空查询、重复查询、忽略搜索结果、
复制粘贴……）+ 10 条奖励（关键词查询、多证据引用、逐步聚焦……），
覆盖"搜索合理性、结果利用、推理逻辑、格式规范"四个维度。

**我的做法**：每条规则是独立可开关的启发式函数（词重叠比、最长公共
子串、问句检测……），有互斥处理（P4 无答案 ↔ B6 格式正确互斥、
P10 复制 ↔ B8 自己的话互斥），防止同一事实双重计分。

**数据**：cap [−0.2, +0.2] 的理由：outcome 是 ±1.0 的主信号，过程
奖励只做"润色"。0.2 = 约 4-7 条规则打满，足以区分行为好坏，不足以
让模型"刷规则分"（reward hacking 的入口）。测量方法：dev 集评估时
22 条规则命中率输出（如 SFT 基线 p4 命中 97.1%、b3 命中 97.1%）。

**反思**：PRM-Lite 本质是"把领域知识编码成奖励形状"（reward
shaping）——用规则表达"什么样的搜索行为是好的"。它的上限受限于
规则设计者的想象力，但作为过程信号的冷启动方案，成本收益比极高。

### Q9. LATA 的动机？advantage = (r-mean)/sqrt(L) 里 sqrt 怎么来的？

**背景**：GRPO 组内比较的一个隐含不公平。

**原理**：长轨迹（多轮搜索）天然 reward 更低——更多出错机会、过程
惩罚规则（轮次过多、查询过长）与长度正相关。结果是好但长的轨迹
advantage 低于差但短的轨迹，模型学到"尽早结束"。LATA 用
`A = (r − mean)/sqrt(L)`（L = 该轨迹 completion token 总数）把不同
长度的轨迹拉回同一尺度。**sqrt 的来历**：把轨迹想成 L 步独立噪声的
和，则总奖励标准差 ∝ sqrt(L)（独立随机变量和的方差 ∝ L）——除以
sqrt(L) 恰好消掉长度带来的方差放大。除以 L 过强（长轨迹被压成 0），
不除则长轨迹方差主导排序。

**我的做法**：`LATAScaler.compute_advantages` 按 question_index 分组
重算（L=0 的空轨迹退回不除），作为 advantage 的后处理开关（--lata）。

**数据**：L=100 → 除 10；L=400 → 除 20（差 2 倍而非 4 倍）。
LATA 和 LLDS 正交：一个管 advantage 公平性，一个管 loss 稳定性。

**反思**：长度偏置是 RL 训练里最容易忽视的隐藏变量——它不只影响
advantage，还影响 PRM 的规则命中。设计奖励时要把"长度"当作
一阶混淆变量检查一遍。

### Q10. outcome reward 和过程奖励各自的优缺点？

**背景**：奖励设计的核心权衡。

**原理**：
- Outcome（只看最终答案）：零成本、客观、与最终目标一致，但**极度
  稀疏**——500 token 轨迹只有一个标量，模型不知道哪个动作导致了
  对错，收敛慢方差大。
- 过程奖励（PRM）：稠密、能定位到具体步骤，但**标注贵**（每步都要
  标对错）、**易被 hack**（优化过程分 ≠ 优化正确率，PRM800K 的经典
  教训）、训练 PRM 本身是另一个项目的成本。

**我的做法**：两层的折中——outcome 为主信号（±1.0），PRM-Lite
规则过程奖励为辅助（capped ±0.2），加在最终 reward 上：
`reward = score_answer + process_reward`。即使答案错，搜索行为好的
轨迹优势也更高，模型先学会"怎么搜"再学会"搜对"。

**数据**：SFT 基线评估时 PRM 均值 −0.0197（它不会搜索，规则在罚）；
GRPO 训练日志里 prm 值随训练转正（搜索行为在变好）。测量方法：
eval 输出 prm/process_reward_mean。

**反思**：面试官如果追问"过程奖励加在最后 token 上还算过程奖励吗"——
诚实回答：算"过程质量的延迟奖励"，梯度传播到整条轨迹的 token
（advantage 是轨迹级的），所以过程信息确实传给了每个动作。

### Q11. 异常轨迹怎么定义的？检测率 2.5% 意味着什么？

**背景**：数据质量层的改进，RL 特有的问题。

**原理**：rollout 会产出大量"垃圾轨迹"（搜索失败、格式坏、截断），
它们参与训练会把噪声梯度灌进策略。RL 不像 SFT 有"人审数据"，
噪声是运行时产生的，必须在训练循环里在线过滤。

**我的做法**：`is_anomalous` 三类：① 最终输出空白；② 搜索额度用尽
（4 次）仍无合法答案；③ 完全没搜且格式错误。处理：advantage 置 0 +
不进训练序列（loss mask 排除）+ 排除后**同组重算** mean/std。
监控指标：rollout/anomalous_trajectories + anomaly_rate 进 SwanLab。

**数据**：10 步验证 160 条轨迹检出 4 条（2.5%）。这个数字的意义：
① 机制行为正确（不是全杀也不是漏杀）；② 2.5% 不高，说明正常
训练中垃圾轨迹是少数——但注意**难题批次会飙升**（实测 anomalous
最高 50/64 条），过滤在高难度分布下更重要。测量方法：训练脚本每步
打印 anomalous 计数。

**反思**：异常检测的本质是"对模型和环境错误做隔离"——模型坏输出
和环境坏反馈（搜索失败）都要隔离，否则 RL 会把"环境故障"学成
"策略行为"（坑 1 就是没隔离的后果）。

### Q12. response_mask 怎么构建？搜索结果的 token 为什么 mask 掉（TITO 协议）？

**背景**：多轮工具调用训练的标志性问题。

**原理**：一条轨迹 = 模型 token 与工具 token 交替。
TITO（Token-In-Token-Out）：agent loop 输入输出全是 token，
`response_mask` 标记每个 token 是否参与训练：
- 模型生成的 token → mask=1（策略的产物，GRPO 优化它）；
- 搜索结果 token → mask=0（**环境**的产物，不是策略的产物）。

mask 掉搜索结果的两个理由：① **防抄答案捷径**——结果 token 参与
loss 会让模型学会"复读结果文本"获得高 logprob，而不是学会推理；
测试时没有结果/结果变了就崩。② **信号稀释**——结果几百 token，
若参与 loss，大部分梯度浪费在"预测结果里的下一个词"（语言模型
任务），而不是"基于证据作答"（推理任务）。

**我的做法**：veRL 版 `SearchR1AgentLoop.run` 里**边生成边填 mask**：
模型 completion 全 extend 1，搜索结果 encode 后全 extend 0，返回
`AgentLoopOutput(response_mask=...)`。比论文版 `<information>` 标签
state_masking 更精确（token 级、不依赖框架对标记字符串的特判）。
本地版等价实现是 `build_training_sequences` 的 loss_mask（prompt 和
tool 部分 0、completion 部分 1）。

**数据**：一次典型轨迹：prompt ~200 token（不训练）、3 轮模型生成
~500 token（训练）、2 次搜索结果 ~600 token（不训练）。

**反思**：mask 的设计本质是回答"**这条轨迹里哪些 token 是策略的
决策变量**"。想清这个，就能自己推导出 prompt mask、pad mask、
tool mask 全部规则。

## 系统工程类

### Q13. FSDP 原理？CPU offload 省了什么、代价是什么？

**背景**：全参数训练 4B 模型的分布式基础。

**原理**：FSDP（Fully Sharded Data Parallel）把模型参数、梯度、
优化器状态**分片（shard）到每张卡**：前向时按需 all-gather 拼出
完整权重，算完立即释放回分片（unshard → compute → reshard）；
反向时 all-reduce 梯度，各卡只持有自己 shard 的梯度。与 DDP 的区别：
DDP 每卡一份完整模型副本，FSDP 每卡只存 1/N——省的是**复制**。

**我的做法**：2×4090 上 FSDP 分片 + `optimizer_offload=true` +
`param_offload=true`：Adam 状态（25.2GB）和参数流式放 CPU，用的时候
搬回 GPU。省了什么：GPU 上 25.2/N GB 的 Adam 状态 + 8.4/N 的参数
常驻；代价：每步参数/状态流式进出，步时 +30-60 秒（PCIe 带宽换显存）。

**数据**：无 offload 每卡 26.7GB ❌（24GB 卡爆）→ 开 offload 后
18.9GB ✓（余 4GB）。测量方法：公式推算 + 日志 allocated 值验证。

**反思**：offload 是"用时间换空间"的经典权衡。小模型（4B）下
步时代价可接受；70B 模型 offload 会让每步慢几倍，那时就该考虑
ZeRO-3 + 更多卡或量化优化器了。

### Q14. 2×4090 训 4B 模型显存怎么算？OOM 排查过程（峰值 20.67GB 定位）？

**背景**：展示显存工程能力的问题，两段式回答。

**原理（显存账）**：bf16 全参数训练，每卡 = 权重 8.4/N + 梯度 8.4/N
+ Adam 25.2/N + 激活 ~1.5 + vLLM 推理池。N=2 无 offload：26.7GB 必爆
（还没算 vLLM 权重 8.4GB）。

**我的做法（排查过程）**：
1. 先按公式开 optimizer+param offload，训练侧只剩梯度+激活 ≈ 5.7GB；
2. 训练能跑但卡在 **update_weights（权重同步）阶段 OOM**：申请
   1.19GB、free 795MB、峰值 allocated 20.67GB——缺口仅 400MB。
3. 六轮逐点定位：观测点显示参数已 CPU offload（allocated 0.00），
   OOM 发生在 load 之后、state_dict 之间——定位到"权重复制到 CPU
   dict 前在 GPU 上物化了全量权重"这一步。
4. 排除项验证：ref 已关（不成立）；layered_summon（只对 LoRA 生效）；
   GC threshold（只能回收 ~3%）。
5. 最终修复（v6）：`get_per_tensor_param_shard()` 取本地 FSDP 分片 +
   FULL_STATE_DICT + offload_to_cpu 流式传输，峰值 12.6GB → ~5GB。

**数据**：峰值 20.67GB / 缺口 400MB / 修复后每卡 18.9GB 余 4GB。
测量方法：补丁打印 torch.cuda.memory_allocated/reserved 观测点。

**反思**：OOM 调试 = 二分定位 + 信日志不信文档（官方 ref offload
在 torch 2.13 下实测不生效）。缺口 400MB 的 OOM 比缺口 10GB 的
难修——大缺口换架构方案，小缺口抠实现细节。
### Q15. veRL 的架构：Ray 角色分工、vLLM 和训练引擎怎么协作、TransferQueue 干嘛的？

**背景**：生产级 RL 框架的架构理解，简历上"veRL 迁移"的必考题。

**原理**：veRL 是 Ray 分布式框架上的 RL 训练系统，单节点 2×4090 部署
下角色分工：
- **Trainer**（driver）：hydra 入口，编排整个 step；
- **ActorWorker ×N（FSDP）**：权重分片训练，前向/反向/优化器；
- **vLLM RolloutWorker ×N**：推理引擎（PagedAttention + continuous
  batching），rollout 阶段的 generate 走这里；
- **AgentLoopWorkerTQ**：持有多轮交互的 agent loop 实例（我自定义的
  SearchR1AgentLoop 就跑在这里）；
- **RewardLoopWorker**：调奖励函数。

**协作方式**：HybridEngine——同一批 GPU 上训练/推理**分时复用显存**
（rollout 时 vLLM 用、训练时 FSDP 用，free_cache_engine 释放 KV cache）；
每步训练完 update_weights 把新权重从 FSDP shard 同步进 vLLM。
TransferQueue（Ascend/TransferQueue 框架）是 agent loop 与 vLLM 之间
的**调度层**：agent loop 的多轮 generate 请求排队、分派、回传——
它解决的是"几千个小请求怎么高效调度给推理引擎"的问题。

**我的做法**：在 veRL main 0.10 上实现了 SearchR1AgentLoop（TITO +
response_mask），对齐了 0.10 的 API（reward.* 键路径、pkg:// 导入、
DictConfigWrap），用 probe 47 项检查守住 API 漂移，并定量分析了
TQ 的调度瓶颈（Q16）。

**数据**：2×4090 训练侧 18.9GB/卡；rollout 阶段 vLLM 池 13.2GB。

**反思**：框架迁移最有价值的部分不是"跑起来"，是**读懂它的调度
架构并定位瓶颈**——TQ 的 51K 操作/步分析就是架构理解的产出。

### Q16. TQ 瓶颈怎么定位的（每步 51K 子操作、PUT_DATA 736/min）？如果让你优化怎么办？

**背景**：我的"瓶颈分析能力"代表作，也是诚实处理"训练没跑完"的
关键问题（配合 Q21）。

**原理**：每步时间 = 各阶段之和。定位瓶颈的标准方法是：分解 +
测量 + 交叉验证。

**我的做法（定位过程）**：
1. **分解**：把每步拆成 rollout（TQ 调度多轮生成 + 搜索）、old log
   prob、奖励、训练、权重同步五段；
2. **测量**：统计每个 agent loop 产生的 TQ 子操作数 ≈ 400 个/loop；
   128 个 loop/步（32 样本 × 多轮内部并发）→ **~51K 子操作/步**；
   TQ 内部统计 SimpleStorageUnit PUT_DATA 吞吐 **~736/min**；
   纯调度时间 = 51K/736 ≈ **70 分钟**，与实测步时 50-70 分钟吻合；
3. **交叉验证（关键一步）**：搜索后端从知乎（0.68s/次）换 DeepSeek
   （1-3s）再换 MiMo（6-14s），**步时几乎不变**——如果瓶颈在搜索
   API，步时应该线性变化；不变说明瓶颈在 TQ 调度，不在搜索。

**数据**：51K 操作/步、736/min、每步 50-70 分钟（日志时间戳）、
搜索延迟 0.68s/1-3s/6-14s（客户端计时）。测量方法：TQ 统计字段
（req_count/avg）+ 后端切换 A/B 对比。

**如果让我优化**（按性价比排序）：
1. **升级/替换调度层**：TQ 的 PUT_DATA 是每请求一次的小批量操作，
   把多轮 generate 的"逐条排队"改成"批量提交"能省掉大部分开销；
   或研究 veRL 里绕过 TQ 的 rollout 路径（TaskRunner 版本差异）；
2. **减少子操作数**：减少 loop 内部状态搬运（合并 metrics/extra
   字段的多次 PUT），或降低组内并发度（n=4→2 牺牲多样性换吞吐）；
3. **异构调度**：搜索 I/O 不占 GPU——把 agent loop 的搜索部分
   移出 TQ 关键路径（纯异步化，不阻塞 generate 队列）；
4. 终极方案：换掉多轮调度范式（如把多轮循环放推理引擎内部），
   这需要框架级改动。

**反思**：定位瓶颈的黄金标准是**交叉验证**——"换掉嫌疑组件看指标
动不动"。直觉（"搜索太慢"）被实验推翻后，才是真正的结论。

### Q17. vLLM 的 max_num_seqs 和 Mamba cache block 什么关系？

**背景**：混合架构模型适配的具体问题。

**原理**：vLLM 的 `max_num_seqs` 是**并发序列数上限**——每个并发
序列要预留一份状态缓存。纯 Transformer 模型的状态是 KV cache
（按 token 分配，PagedAttention 分页管理）；Qwen3.5 是 Transformer+
Mamba 混合架构，**Mamba 层有固定大小的 recurrent state（cache
block），按序列数预分配、不可分页**。所以 Mamba 模型的并发上限 =
Mamba cache block 总数（229），设 max_num_seqs 超过它，vLLM 启动
即报错。

**我的做法**：报错信息
`max_num_seqs (256) exceeds available Mamba cache blocks (229)`
直接给出了上限 → `max_num_seqs=229`。

**数据**：256 失败、229 通过（报错信息即证据）。

**反思**：混合架构模型的并发约束由**最受限的组件**决定。这类问题的
通用解法：先读报错（数字都在里面），再查该组件（Mamba cache）的
分配模型。另外 229 的并发对 GRPO 的组内采样够用（我们 batch 才 32）。

### Q18. probe 脚本的设计方法论：为什么训练前要跑 47 项检查？

**背景**：工程纪律问题，考的是"成本意识"。

**原理**：**probe 失败的成本是 0，训练失败的成本是 GPU 小时**。
服务器 ¥4.36/h，一次"跑 10 分钟才发现 import 错"就是 ¥0.7+，
而这类错误本地 1 分钟就能查出来。probe 的设计原则：按"必然炸 →
概率炸"排序，覆盖所有花 GPU 钱之前能验证的东西。

**我的做法**（probe_verl_api.py，47 项、7 节）：
1. agent-loop API 签名/注册表（veRL main 天天变，API 漂移第一道防线）；
2. worker 式实例化 + chat template 冒烟（模拟 Ray worker 环境，不止
   driver 进程——坑 9 的教训）；
3. hydra 全量 compose + key-drift 扫描（hydra 对不存在的键 hard-fail，
   compose 本身就是检查）+ wiring assert（PRM 开关真的传进了 reward）；
4. reward 函数 import + 签名 + 假 DataProto 冒烟（字段流转走一遍）；
5. 库版本 + GPU + transfer_queue/flashinfer 存在性；
6. 数据文件 + 列名 + 启动脚本陈旧参数扫描；
7. --live-search **实弹搜索**（API key 真的有效——坑 1 的教训）。

**数据**：probe 抓出过的问题：reward_fn 导入路径、API 漂移 3 处、
配置键移动、数据列缺失。0 FAIL 才启动是铁律。

**反思**：probe 的本质是**把"运行时才发现"的问题前移到"花第一分钱
之前"**。清单越长，说明你踩过的坑越多——47 项里每一项背后都是
一次真实失败。

### Q19. 教师蒸馏怎么做？397 条够吗？为什么 QLoRA rank=32？

**背景**：数据工程的三个子问题。

**原理**：RL 冷启动需要先让模型会"工具调用的格式"。教师蒸馏 =
让强模型（DeepSeek Chat）示范正确轨迹，SFT 学格式和推理模式，
RL 再优化策略。

**我的做法**：
- **蒸馏 prompt 设计**：三段式节标记（BEGIN ASSISTANT / BEGIN TOOL /
  END TOOL）+ 协议约束（每轮一个动作）+ 教师**模拟**搜索结果
  （自带知识生成伪检索结果）+ 两个 few-shot（简单题 1 搜 / 多跳题
  2 搜，示范 query 迭代）。抽样 NQ 200 + HotpotQA 200，成功 397 条
  （3 条解析失败），断点续传 + 失败原样落盘。
- **397 条够吗**：对"教格式"够（SFT loss 1.65→0.11，模型学会了
  输出 tool call 结构），对"教知识/推理"肯定不够——但这不是 SFT
  的任务，推理能力是 GRPO 在 17 万训练样本上练的。分工明确是
  397 条够用的前提。
- **rank=32**：SFT 阶段分布变化大（从不会工具调用到会），用
  r=32/alpha=64（缩放 alpha/r=2）；GRPO 阶段只需策略微调，降到

**数据**：loss 1.6515→0.1143（150 steps/3 epochs）；82MB adapter；
合并后 7.9GB fp16。测量方法：训练日志 LossLogCallback 每步打印。

**反思**：蒸馏的诚实局限要说——模拟搜索结果 ≠ 真实检索（README
已知限制 4），所以 SFT 模型"会格式不会检索"（dev 集搜索 0 次）。
面试官问"为什么不用真实搜索生成蒸馏数据"，答案：当时 DeepSeek
Search API 的用量与稳定性不可控，而格式教学不需要真实结果；
如果重做我会加一半真实检索轨迹。

### Q20. SFT 冷启动为什么有效？纯 RL 从 base 开始会怎样？

**背景**：SFT+RL 两段式 vs 纯 RL 的对比。

**原理**：RL 的奖励在"行为空间"里非常稀疏——base 模型随机探索
出"恰好格式正确的工具调用"概率极低，奖励信号几乎为零，收敛极慢
甚至不收敛（探索效率问题）。SFT 先把策略初始化到"会格式"的区域，
RL 从这个区域开始做局部优化——**SFT 负责把起点挪近解，RL 负责
爬坡**。DeepSeek-R1 同款思路。

**我的做法**：蒸馏 397 条 → QLoRA SFT → 合并 → GRPO。

**数据**（本项目最有说服力的对比）：
- SFT 模型（未 RL）：dev 70 题 EM **1.43%**、平均搜索 **0 次**——
  只会格式，不会工具使用的行为闭环；
- v2 纯 RL（base 起训，key 有效）：correct_rate **81.2%**（step 3
  peak）——纯 RL 也能学会（Search-R1 论文结论的复现），
  但经历过 56 步崩到 3.1% 的死亡螺旋；
- SFT+GRPO 让起点更好、训练更稳（格式不再是从零探索）。
测量方法：eval_local.py greedy + 训练日志。

**反思**：诚实结论：在本项目里"纯 RL vs SFT+RL 的最终性能对比"
没有严格完成（veRL 阶段停摆 + E2-D 结果断档），但两个事实是硬的：
SFT 单独不工作（1.43%）、纯 RL 能工作但会崩（死亡螺旋）。SFT 的
价值在**稳定性**和**格式起点**，不在最终分数。

### Q22. 「比原论文提升 27%」怎么算的？比较的基线公平吗？

**背景**：必须能自圆其说的问题，考学术诚实。

1. **数字怎么来的**：81.2%（本地管线 correct_rate peak）相对论文
   Search-R1 报告的 ~64%（HotpotQA 7B 结果 63.7% 附近）的**相对
   提升**：81.2/64 ≈ 1.27 → "27% 相对提升"。
2. **为什么不公平（必须主动说）**：① 评测分布不同——我的 81.2%
   是**训练过程中批次内的 correct_rate**（每步 64 条轨迹的 EM 比例，
   PyTRIO 日志），不是留出测试集；② 模型不同（Qwen3.5-4B vs 论文
   的 Qwen2.5-7B）；③ 训练数据分布不同（我的训练集是 NQ+HotpotQA
   混合 vs 论文各数据集独立）。**这不是同口径对比，不能在论文意义
   上引用。**
3. **什么是我敢说的**：① SFT 基线 1.43% → GRPO 81.2% 的**同口径
   前后对比**（同一管线、同一批指标定义）证明了 GRPO 在学；
   ② 论文的核心结论（RL 让模型学会搜索）被独立复现；
   ③ LLDS 防崩效果（v1 崩 1.6% vs v2 恢复 54.7%）是**同配置
   单变量**对比，这个可以硬说。

**反思**：包装项目时"27%"是吸引眼球的话术，面试时是检验诚实度的
试金石。正确姿势：**先说数字再主动说口径局限**——面试官对你
"知道自己的数字哪里站不住"的印象，远好于"数字漂亮"。

## 结果与分析类

### Q23. 哪些指标衡量？EM/Format/correct_rate 各是什么？

**背景**：指标定义是基本功。

**原理**：
- **EM（Exact Match）**：normalize 后（小写、去标点、去冠词、合并
  空格）的答案字符串与参考答案**完全相等**才算对——最严格，没有
  部分分；
- **Format rate**：输出恰好一行 `Answer: xxx` 的轨迹比例——协议的
  遵守度；
- **correct_rate**：训练日志里的批次内 EM 比例（即"当前步这批
  轨迹答对的比例"），与 EM 是同一个量，只是统计口径（批次内 vs
  留出集）。

**我的做法**：eval_local.py 输出 em/macro（70 题平均）+ **分源 EM**
（em/nq、em/hotpotqa、em/triviaqa 等 7 个）+ format/rate + 平均搜索
次数 + no_search_rate + PRM 规则命中率。分源拆分的原因：NQ 单跳、
HotpotQA 多跳，混在一起会掩盖能力差异。

**数据**：SFT 基线：EM 1.43%、format 2.86%、search 0 次；
训练中：correct 81.2%、search 1-2.8。

**反思**：指标组合要能回答三个问题：答对了吗（EM）、守规矩吗
（format）、真的在用工具吗（search 次数）——三个一起看才能发现
"reward 涨了但模型在瞎猜"。

### Q24. 你的改进里哪个贡献最大？有消融吗？没有消融怎么回答？

**背景**：没有完整消融是个人项目的常态，关键是怎么诚实回答。

**我的做法**：
1. **哪些有单变量对比（能硬说）**：LLDS——E1-A（无）vs E3-B（有）
   同配置对比：无 LLDS 永久崩（56 步 3.1%），有 LLDS v2 低点可恢复、
   最高 81.2%。贡献最大我选 LLDS：**没有它训练根本跑不完**，其他
   改进都是在"能跑完"前提下的优化。
2. **哪些没有严格消融（诚实说）**：PRM-Lite、LATA、异常过滤、
   SFT 冷启动——它们在同一管线上叠加验证过（开关独立、逻辑正确、
   单元测试覆盖），但没有做"开/关 × 多步数"的 A/B。原因：预算
   （每个 50 步实验 ¥30-60）和训练时长（步时 16min/50-70min）。
3. **怎么把劣势讲成能力**：承认没有消融后，主动讲"如果做消融
   怎么设计"——E6-B（+PRM）vs E6-A（纯 GRPO）单变量矩阵其实
   **已经设计好了**（deploy 文档 §5.5），只是没跑完。设计能力
   在，执行受预算限制——这是个人项目的合理边界。

**反思**：面试官问消融，一半是在考"你知不知道消融的重要性"。
承认局限 + 展示消融设计 + 讲清预算约束，比硬编一个"提升 3%"诚实
得多，也专业得多。

### Q25. 预生成缓存失败的教训？

**背景**：一个 ¥0 就能避免的失误，讲出来显示复盘能力。

**原理**：缓存的正确性取决于**key 空间的一致性**——写入时的 key
必须等于查找时的 key。

**我的做法**：为了省搜索 API 调用，预生成 2000 条搜索缓存
（key = 训练问题原文，如 "total number of death row inmates in
the us?"）。训练时查找用**模型生成的 query**（"death row inmates
statistics"）——两个 key 空间根本不重合，命中率 0%，2000 条
白生成。

**数据**：命中率 0%（日志 cache hit/miss 计数）。

**反思**：教训三层：① 缓存 key 必须和运行时查询 key 一致，
**先小样本验证命中率再全量部署**；② 这个错误本地 5 分钟就能
验证，却花在了服务器上——违反了自己"先本地验证再上传"的纪律；
③ 正确方案是运行时缓存（同 step 内相同 query 自然命中），
我最后用的就是这个。

## 行为类

### Q26. 项目里最难的技术问题？怎么一步步定位的？

**背景**：考问题解决方法的完整叙事。

**我的做法**：选 update_weights 的 OOM（缺口仅 400MB 的那个），
因为它的定位过程最能展示方法论：
1. **量化现象**：错误信息本身给了三个数——申请 1.19GB、free
   795MB、峰值 allocated 20.67GB → 缺口 ~400MB；
2. **打观测点**：在可疑路径（load 前后、state_dict 前后、offload
   后）插 allocated 打印，二分定位 OOM 发生的精确区间——load 之后、
   state_dict 之间；
3. **排除法**：把候选原因列清单逐一验证（ref 已关 ✓ 排除；
   layered_summon 只对 LoRA 生效 ✗ 排除；GC threshold 只能回收
   3% ✗ 不够）；
4. **读源码找方案**：`get_per_tensor_param_shard` 官方注释
   "yields each rank's local FSDP shard"——不 unshard 不 all-gather，
   从根上消掉峰值；
5. **验证**：修复后日志 "after update_weights, allocated 0.00"。

**数据**：峰值 12.6GB → ~5GB，OOM 消除。

**反思**：难的从来不是"知道答案"，是**在六轮调试里坚持"观测→
假设→验证"而不是"猜→试"**。每轮都留下一个观测点，下一轮就
站在上一轮的肩膀上。

### Q27. 项目里最大的失败？学到什么？

**背景**：考自我认知与成长，答案要真。

**我的做法**：最大失败 = **veRL 全参数训练没跑完**（50 步目标，
停在早期 step）。诚实拆解：
- 时间账：把大量预算花在"修环境"（OOM/API 漂移/DNS 等 12 轮），
  留给真正训练的窗口太小；
- 选型账：没在部署前 benchmark TQ 的调度吞吐——如果先花 10 分钟
  测一下，51K 操作/步 vs 736/min 的矛盾在**开 GPU 之前**就暴露了，
  可以直接换方案，省下 ¥20+ 和 3 天调试；
- 决策账：止损规则执行得太晚（早该在步时 >12min 的第一天就停）。

学到的三件事：① **瓶颈要部署前测，不要训练中撞**（probe 文化）；
② 止损规则写了就要执行；③ 预算纪律 = 工程能力的一部分。
附带的正面产出：TQ 瓶颈的定量分析成了项目里最硬核的分析成果
（Q16）——失败被打捞成了产出。

**反思**：面试官不期待你没有失败，期待你**失败的账算得清**。

### Q28. 如果重新做一遍，会怎么做？

**背景**：考全局优化视角，把前 27 题的教训串起来。

**我的做法**（按时间线重排）：
1. **选型阶段**：框架评估加一项"多轮 agent 的调度架构 benchmark"——
   部署前 10 分钟测出 TQ 吞吐问题（Q21/Q27 的根因）；
2. **算法阶段**：先本地管线跑完消融矩阵（LLDS/PRM/LATA 单变量
   各 50 步，¥13/个，总价 <¥50），拿到**有消融的结论**再去 veRL；
3. **数据阶段**：蒸馏轨迹一半用真实检索生成（修掉"模拟搜索"
   的局限），SFT 数据加 10 倍量级看 EM 是否随数据涨；
4. **训练阶段**：veRL 只做"迁移成功"的最小验证（10 步），
   全量训练等 TQ 优化或换调度方案后再跑；
5. **全程**：probe 文化 + 止损纪律从第一天执行，每花一笔钱
   都有对应的验证目标。

**反思**：重做一遍的关键词是**顺序**——把"贵的验证"（veRL 全量）
放在"便宜的验证"（本地消融、调度 benchmark）之后。项目最大的
成本从来不是算力，是顺序错了导致的返工。
